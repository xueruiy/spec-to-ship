# 按任务进入研发

用户一次进入后，由本入口选择并实际执行同包 Matt 方法，在已授权范围内连续衔接；不是另一套开发方法或自动状态机。保留用户直接调用原生 Skills 的方式，不把所有任务带过一遍澄清、spec、tickets、实施、验收。

## 先判断本次要完成什么

先读用户请求和已有会话授权，区分探索、明确改动、诊断、只测试、只审查、验收、恢复或暂停。只读取判断所需的项目 AGENTS／CLAUDE、已有 tracker／domain 配置、用户给出的材料及相关代码状态。

用一两句说明本次目标、可复用依据与选定下一步；范围已经明确就行动，不额外要求用户批准路线。需要用户决定的产品行为、范围或权限，提出具体问题并等待答案后再做依赖该决定的工作；其他已授权且不依赖的探索可继续。

## 连续推进已授权工作

用户要求按任务依赖连续实施时，完成一项或解除阻塞后直接继续，不反复等待“继续”，不让用户重复调用已触发的同一入口。常规实现/测试细节沿用授权；新产品决定、额外权限及真实宿主限制仍需满足，但不要求用户逐阶段重新调用 Skill。

每轮辨别范围内调整、实现缺陷、追加／变更需求、仅讨论或独立新任务，并单独核对有效授权。采用用户最新决定；已授权就继续，变化及时同步原有依据、相关任务和标准。实现受限时列出未完成部分或具体取舍，不静默缩减范围。写入材料前核对原目标、范围和完成标准：同一任务更新原材料，跨范围的新任务按项目约定另定归属并引用旧依据，不能仅因主题相关就追加到历史计划。话题变化不取消旧任务；普通追问不新增文件，持续追踪才成文，事实、已确认决定和建议分别标明。

实施前定位可观察的结果标准，验证用户实际完成点而非仅中间步骤。性能改进核对主要耗时和可比条件下的结果；复用能力核对当前场景的适用条件与限制，具体检查由业务标准决定。界面变更尽早展示首个可操作的关键交互，不强制独立设计阶段。

已授权交付工作按需主动读取并执行 [sts-acceptance](../sts-acceptance/SKILL.md) 和 [sts-closeout](../sts-closeout/SKILL.md)，不用用户逐个触发；只讨论、检查或暂停仍按本轮范围结束。报告检查与知识同步实际执行了什么，技术验证和用户认可分开，不能代签用户结论。

委派时传递需求、范围、授权和验收标准；回收时核对版本与证据，主任务负责集成与整体验收。独立会话重新读取适用项目规则和 Skill，创建会话遵守宿主及用户授权。

## 选择最小足够入口

| 当前情况 | 下一步与可用能力 |
| --- | --- |
| 只有想法，用户结果或边界不清楚 | 核实可查事实，再用 [grill-with-docs](../grill-with-docs/SKILL.md) 澄清；只有需要持久规格且无足够材料时再建议 [to-spec](../to-spec/SKILL.md) |
| 已有 PRD、技术文档、计划或进行中任务 | 先核对有效版本、确认记录和当前代码。材料足够就直接作为原生 implement／to-tickets 的输入，不因文件不叫 spec 而重写；只补缺口或冲突 |
| 改动明确且已授权 | 单一低风险改动可直接实施必要修改与检查，在现有任务或回复中简要留证，不强制新 spec／tickets／验收文档。需要原生实施能力时用 [implement](../implement/SKILL.md)，它接受 spec 或 tickets，不以先拆票为前提 |
| 多个可独立验证结果或真实依赖需要管理 | 用 [to-tickets](../to-tickets/SKILL.md) 引用已有 plan／spec／讨论／PRD 与技术文档，按需拆分；不是所有任务的必经步骤 |
| 异常或性能偏离已有预期 | 保留症状、基线与环境，用 [diagnosing-bugs](../diagnosing-bugs/SKILL.md) 建立复现和验证。仅诊断授权时停在定位，不因原生包含修复步骤就改代码 |
| 想“优化体验／行为”但新结果未定义 | 先明确要改变什么及如何判断，不把偏好当缺陷；明确可度量的目标后再进入实现或诊断 |
| 只测试、只审查或只验收 | 仅完成指定范围：测试按项目已有命令／操作执行并报告；审查用 [code-review](../code-review/SKILL.md) 或明确标为工作区人工审读；验收用 [sts-acceptance](../sts-acceptance/SKILL.md)。失败只报告，不默认修复或进入交付 |
| 恢复中断、准备交付或暂停 | 先核对版本／工作区／旧证据和未决事项，从真实未完成处继续。需要交付再完成适用检查与验收，用 [sts-closeout](../sts-closeout/SKILL.md) 同步知识；只暂停就保留未完成结论，换会话按需 [handoff](../handoff/SKILL.md) |

已确认的 PRD／技术文档、原生 spec、ticket 或足够明确的讨论都可作为规格依据，指出权威位置即可。缺少可观察标准时回到澄清，不能从代码“提炼”出据称事先确认的标准。保留原生 spec／tickets 的结构，不复制或修改 Matt 的流程正文。

## 实际执行同包方法

- 确认当前 Skill 所属 spec-to-ship 插件的实际安装路径与宿主可用入口。所有 Matt 与 sts 依赖按本文件相对链接从同一插件的 `skills/` 读取；不凭短名选择同名全局或旧项目版本。包内文件存在不证明宿主已发现。业务规则、配置与任务材料始终从当前业务项目读取，不能写入插件缓存。
- 选中后实际读取并执行适用 Skill 及必要依赖，不以推荐命令替代执行。当前包的调用元数据已适配自动选择；无需用户再次显式触发。依宿主支持的机制加载并执行，不能把只读文件或普通操作称为完成 Matt 方法，也不能冒称使用了不存在的 Skill 工具。若实际加载的是旧版受限入口，报告版本或发现缺口，不绕过其策略。
- 需要系统访谈时执行 grill-with-docs 及 grilling、domain-modeling；普通事实追问不强制访谈。决定收敛且本轮需要持久规格才执行 to-spec；已有足够材料直接复用。按需拆票，已授权实施才执行 implement。原生方法中的确认优先复用已有明确决定，未决取舍仍提问；只讨论不能自动升级为规格发布或实施。
- 宿主调用映射：有原生 Skill 调用工具时使用该工具；Codex 文件加载型宿主中，将正文中的“Call/Load Skill”映射为读取同包对应 SKILL.md 并实际执行其指令与所需资源，递归处理依赖。报告为“通过文件加载执行”，不声称发出了 Skill 工具调用。只读取不执行不算完成方法；没有可用加载机制或缺少必需子 Agent、业务工具时，报告具体受阻步骤，不模拟结果或跳过依赖。
- 用户要求接入或已授权工作确需首次配置时，实际执行 [setup-matt-pocock-skills](../setup-matt-pocock-skills/SKILL.md)。已配置项目不重跑 setup；仅测试已有命令、明确小改动等不依赖 tracker 的工作，不因缺少 setup 文件停下。

## 版本、授权和结束点

原生 implement 包含提交动作，diagnosing-bugs 包含修复，均受用户本次授权约束；测试、诊断、审查不隐含修复，实施不隐含推送／发布。缺失提交授权时不要为了让原生审查产生差异而自行提交。

先核对规格、固定基线和本次改动状态，再选择审查：未提交内容直接审读暂存／未暂存差异及相关新增文件，同时核对项目规范和需求正确性；已提交内容用 [code-review](../code-review/SKILL.md)；混合状态明确两部分及相互影响，复用有效证据。工作区人工审读记录范围、发现和版本依据，不冒称原生或独立审查。

原生 `base...HEAD` 不覆盖工作区，implement 内置 review 后 commit 的顺序保持不变，但内置调用不证明本次改动已覆盖。不额外运行明知无有效差异的原生审查。交付内容及相关依据、上下文与已有证据一致时可复用，不因提交动作完整重审；修改、冲突或集成变化补审受影响部分。明确指定的原生审查遵守原生调用条件，不能用人工审读冒充。

继续或恢复任务时比较旧记录与当前代码、相关未提交改动、环境及配置，核对有效授权、未完成项并标记需重新验证的范围。工具或环境受阻记录具体缺口、原因、恢复条件和入口；条件满足且授权仍有效时继续，不默认创建后台调度。先解决仍待用户决定的问题，不把历史建议当批准，也不为已有足够标准重新组织整套文档。

结束时简述实际执行的 Skill 与关键结果、证据对应版本、未完成原因及下一步；未执行的建议不列为完成。只测试的终点是测试结果，只审查的终点是发现与覆盖，暂停的终点是可恢复状态；这些都不自动变成产品验收或成功交付。证据去敏、保存现有产物引用，不另建状态数据库或整套重复报告。
