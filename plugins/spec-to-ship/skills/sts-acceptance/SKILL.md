# 产品验收

本文件与模板来自当前 spec-to-ship 插件；需要其他 Skill 时绑定同一插件的 `skills/`，不选择同名旧版本。业务规则、任务记录和知识更新均定位当前业务项目，不能写入插件缓存。

读取业务项目适用的 AGENTS.md、`docs/agents/issue-tracker.md`、用户指定的 spec、PRD／技术文档或其他已确认标准、实际存在的相关任务记录及当前实现的测试、回归和审查证据。沿用项目产物位置；需要独立记录时，本地 tracker 默认写到同一功能目录的 `acceptance.md`。小任务可在已有任务或回复中保留结果与用户决定，不强制新建验收报告。不要求单独 PRD／技术方案或 R／AC 编号。

## 验收依据

- 定位实现前已明确并确认的用户行为、边界和完成标准，用权威材料的章节、条目或原文短引建立对应关系，保留其版本或快照；材料足够时不重新生成 spec。
- 标准缺失或含糊时，把具体问题交回规格澄清；只继续不依赖该问题的检查。不根据现有实现倒推标准，不擅自降低标准或把新行为当已确认需求。
- 按改动影响验证用户最终结果及必要的后续使用，不以中间操作成功代替；测试和代码审查只证明实际覆盖的部分。业务项目确定具体检查项，不套用其他项目清单。
- 性能验收以用户感知的实际完成点为依据，在可比条件下核对改善；区分不同使用条件、即时反馈与完成。复用能力需验证适用条件及当前场景行为，不能仅确认已接入。

## 执行与记录

1. 确认代码 commit／分支，暂存、未暂存、未跟踪的相关改动，保存脱敏 diff 或快照引用；记录环境、配置差异、时间、执行者。已有完全一致的记录可引用，不能仅凭 HEAD 一样推断工作区一样。
2. 按已确认标准执行或引用有效证据，逐项记录实际表现、证据入口和结果：未运行、通过、未通过、阻塞、需重新验证。失败或未执行都不能算通过。
3. 相关代码、配置、环境或标准变化后，保留旧结论及版本，标记受影响项目需重新验证；更新当前结果表，不强制建立新批次目录。原生 code-review 的 base...HEAD 审查不覆盖未提交内容；若用它作审查证据，核对审查 HEAD 与差异范围，明确未覆盖项。工作区人工审读单独标明方式、范围和内容依据；交付内容及相关依据、上下文一致时可复用，不能因提交动作要求重复全审，也不能把人工审读冒称原生审查。
4. 实现缺陷交回开发修复、重测；需求变化单独核对已有确认及授权，采用最新明确决定，更新原有权威材料及受影响任务和验收项，不重复索要已给出的确认。实现受限不能静默删减标准。不要为验收结论修改产品代码，除非已有修复授权。
5. 汇报证据支持的技术观察及尚需用户判断的内容。最终产品决定单独记录确认人、时间、范围和依据，Agent 不代签。整体通过需要所有必需项的当前有效证据及用户确认；否则写未通过或待确认／暂缓。

## 当前结果与必要证据

验证受阻时记录具体未验证项、原因、恢复条件及入口，回传当前任务保留；切换话题不能将其算作完成。

报告顶部按标准、实际结果、版本与证据、缺口集中展示，分别说明实现完成范围、验证结果和用户决定；历史过程放后面或链接引用，不让用户自行拼出有效结论。连续的同类交互调整合并记录，按功能/缺陷命名，保留变化依据。

普通测试与构建保留命令、范围、时间及实际结果即可；优先复用有效证据，不默认保存每轮全量日志、文档副本与源码包。必须保留足够版本依据、关键失败及最终有效复验；精简不得把未运行、失败或旧通过升级为当前通过。删除文件需有有效清理授权，先查引用并修复链接。

交给用户时提供具体页面/产物入口、尚需人工判断的项目和可确认范围；技术通过与用户决定分别记录。

需要结构化记录时用 [验收记录](assets/acceptance.md)，已有记录足够时直接更新。不要复制完整规格材料或测试报告；不要写入凭证、敏感日志。执行与外部操作遵从用户有效授权；使用此 Skill 不额外授予发布或部署权限。
