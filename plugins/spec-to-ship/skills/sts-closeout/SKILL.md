# 收尾与知识同步

本文件与模板来自当前 spec-to-ship 插件；需要其他 Skill 时绑定同一插件的 `skills/`，不选择同名旧版本。业务规则、任务记录和知识更新均定位当前业务项目，不能写入插件缓存。

读取业务项目适用的 AGENTS.md、`docs/agents/issue-tracker.md`、`docs/agents/domain.md`、本次实际存在的需求／技术材料、任务、验证和验收记录，以及已存在的相关模块知识。跟随项目目录；需要独立记录时，本地 tracker 默认在功能目录写 `closeout.md`。小任务可以在已有任务或回复中简述交付、遗留和知识处置，不强制新建收尾文件，也不要求补齐不存在的验收报告。不强制另建开发总结、PRD、设计文档或测试套件。

## 交付整理

- 记录实际交付范围、最终 commit／分支及相关未提交差异或快照，引用有效产物。缺少验证或用户验收就如实说明，不能补写“通过”。暂停或终止也可以收尾，保留未完成结论。
- 将遗留问题指向后续任务或待决定事项，注明影响与下一步。索引只做导航，不复制所有 ticket 状态。

## 面向用户的交付

给出当前页面或产物入口、剩余人工判断项及确认范围，不能只写“待验收”。已授权后续工作继续推进；收尾不自动扩大为发布。

检查实际产物是否重复：普通日志汇总结果，同类交互报告可合并；保留关键失败、有效复验和必要版本依据，不固定文件数或批次目录。在有效清理授权内精简并修复引用；否则只列建议。尊重项目对 `.scratch` 的忽略/提交选择，不自行改变Git策略。

## 当前知识同步

1. 从代码、测试、需求或技术决定及验收证据中提取值得长期维护的业务规则、模块约束和可复用经验，附支持引用。
2. 与现有权威位置逐项核对，决定新增、更新、替换、标记失效或无需更新。先处理矛盾；不凭历史报告直接覆盖当前事实。
3. 区分已验证事实、已确认决定、待验证猜测。新业务规则无确认依据时留在待决事项；猜测转验证任务，不写成正式约束。
4. 在已有权限范围内更新唯一权威文档：`CONTEXT.md` 只放领域词汇，模块文档放当前业务行为与实现知识，已有 ADR 记录重要取舍，AGENTS.md 管执行要求。已有来源只引用，不复制一套。
5. 代码图谱或自动生成知识图只作导航，按项目既有方式刷新；不把图谱推断当已确认业务事实，不手工改生成物。不因每个任务创建 ADR、Skill 或新模块文档。
6. 收尾记录注明知识更新动作、位置和依据；无值得沉淀内容明确写“无需更新”及原因。尚待授权或确认的更新写待处理，不声称完成。

## 模块现状文档

按业务模块维护当前职责、已实现行为、数据归属、限制、关键代码/测试入口和最近核对版本；区分已实现、已验证与待确认，未来需求留在任务材料。更新对应章节，不追加任务流水。

旧文档有偏移时先核对代码与已确认决定，纠正或替换过时描述。需要迁移时标清试稿、替代范围与唯一权威来源；删除旧文档或切换全项目导航按授权进行，不能仅复制一份就宣称完成迁移。中文项目优先采用简短中文业务名称，`doc/modules/剪辑工作台.md`仅是例子，不强制目录，也不改工具约定文件名。

正式模块文档直接包含必要结论和代码/测试引用，不依赖被忽略的任务目录才能理解。旧验证不自动适用于新HEAD；注明本次实际核对了什么，未重验写明未重验。

需要结构化记录时用 [收尾记录](assets/closeout.md)。不要收集所有调试过程或原始会话，不保留密钥与敏感日志。历史任务用于追溯，后续开发优先读当前模块知识。收尾不自动提交、推送、发布、部署或删除任务目录，这些操作遵从用户独立有效授权。
